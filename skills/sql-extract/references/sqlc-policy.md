# SQL-first + sqlc Policy

Apply this policy to the database layer of the migration target. Configuration and SQL examples are illustrative; this repository does not include an executable target database or generated code.

## Files and Generation Boundaries

```text
db/
├── schema.sql
└── queries/
    └── notice.sql
sqlc.yaml
internal/dbgen/       # Generated by sqlc; do not edit directly.
```

Existing migrations may serve as schema input. Define the authoritative source and generation direction instead of maintaining two schemas manually. Keep schema DDL and data snapshots as separate artifacts. Do not assume schema input fully describes actual database triggers, procedures, or configuration.

Example MySQL configuration:

```yaml
version: "2"
sql:
  - engine: mysql
    schema: db/schema.sql
    queries: db/queries
    gen:
      go:
        package: dbgen
        out: internal/dbgen
        sql_package: database/sql
```

`version: "2"` identifies the configuration format. Pin the sqlc binary version separately in project tooling. Configure type overrides only after checking actual DDL and driver behavior. See the [official configuration documentation](https://docs.sqlc.dev/en/latest/reference/config.html).

Business code must not execute raw SQL or construct SQL strings. Internal `database/sql` calls generated by sqlc are expected. Distinguish infrastructure connection/pool/health check/transaction lifecycle management and SQL used by migration, fixture, and observation tools. All business queries within a transaction must use the instance returned by `queries.WithTx(tx)`. See the [official transaction documentation](https://docs.sqlc.dev/en/latest/howto/transactions.html).

## Values and Identifiers

| Original pattern | Handling policy |
| --- | --- |
| User values interpolated into strings | Replace with value placeholders; verify type, NULL, and conversion semantics |
| Optional WHERE clauses | Split into a finite set of semantically equivalent static queries; check NULL/empty values and performance |
| Dynamic ORDER BY | Static queries by column/direction with allowlist dispatch |
| Per-board tables/configured prefixes | Generate static SQL from a deployment-fixed list; use allowlist dispatch at runtime |
| Variable-length IN lists | Check sqlc capabilities for the pinned version/driver; verify empty lists, duplicates, NULL, and size boundaries |
| Arbitrary runtime DDL/identifiers | Record UNSUPPORTED and impact if generation/redeployment cannot preserve the behavior |
| Unsupported dialect/functions/procedures | Confirm through actual generation; rewrite while preserving meaning or record UNSUPPORTED |

Do not replace identifiers or SQL keywords with value placeholders. Do not add fallbacks that escape input and concatenate SQL strings. Do not claim unconditional support for dynamic queries.

The official documentation states that `sqlc.slice`, which can handle variable-length IN lists, cannot be combined with prepared queries. Check target configuration and empty-list handling before adoption. See the [official macro documentation](https://docs.sqlc.dev/en/latest/reference/macros.html).

Take particular care with applications such as GNUboard, where creating a board creates a table. Fixing table lists at deployment may support existing reads without preserving runtime board creation. State whether regeneration and redeployment are acceptable in the contract. Otherwise report the behavior as unsupported; do not unilaterally redesign the data model by consolidating tables.

## Extraction Example and Semantic Preservation

For an original query that reads one row by ID from a fixed table, with columns and uniqueness confirmed in actual DDL:

```sql
-- name: GetNotice :one
SELECT wr_id, wr_subject, wr_content
FROM g5_write_notice
WHERE wr_id = ?;
```

Choose explicit SELECT columns and `:one` to match original result consumption. Do not add LIMIT or ordering absent from the original for convenience. The schema determines the Go ID type; do not assume it is always `int64`. See the [official MySQL example](https://docs.sqlc.dev/en/latest/tutorials/getting-started-mysql.html).

Query parameterization alone does not establish request safety or equivalence. Check original database conversion, errors, and HTTP behavior for `'01'`, `''`, missing values, out-of-range numbers, and nonnumeric input. Returning 400 on `ParseInt` failure is a separate contract change. Link security differences to approval records and mismatches and verify normal inputs too.

## Completion Evidence

1. A complete inventory of original SQL sites/construction branches maps to queries, generated methods, and scenarios, with unconfirmed items identified.
2. `sqlc generate` succeeds with the pinned version, input and output hashes are recorded, and regeneration is identical.
3. Go builds with the actual generated types. Relevant scenarios cover empty results, NULL, unsigned/decimal/time values, affected rows, generated IDs, and transaction behavior.
4. PHP and Go responses and database effects are compared from equivalent restored initial state, with rollback, authorization, dynamic branch, and ordering gaps reported.
5. Generated-file edits and direct application SQL execution have been reviewed, and permitted infrastructure boundaries are documented.

Report missing tools, generation failures, and unexecuted checks accurately. sqlc is neither a schema migration runner nor a functional equivalence verifier. See the [official generation documentation](https://docs.sqlc.dev/en/latest/howto/generate.html).
